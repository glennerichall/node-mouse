# Fiabilité — REL-002 — 2026-10-08

État: terminé

## Objectif

Rétablir l'acceptation des commandes d'entrée après redémarrage du service et
fiabiliser le cycle de reconnexion côté client.

## Diagnostic

Le contrôleur Wayland conservait un backend marqué indisponible après un échec
d'ouverture de uinput au démarrage. Les méthodes d'entrée retournaient alors
sans réessayer l'autorisation, même lorsque le périphérique redevenait
disponible.

## Modifications

- Le contrôleur réessaie l'autorisation du backend uniquement pour
  wayland-uinput avant une commande clavier ou souris.
- Les commandes restent ignorées lorsque le backend n'est pas prêt.
- Le portail Wayland conserve son autorisation interactive explicite et ne
  déclenche pas de demande depuis une commande d'entrée.
- Le transport expose les états connecting, connected, reconnecting et
  unavailable via le pub/sub client.
- La reconnexion Socket.IO est bornée à dix tentatives avec un délai maximal de
  deux secondes.
- Les commandes émises pendant une coupure ne sont plus tamponnées par
  Socket.IO : elles sont refusées et publiées comme transport.command-dropped,
  ce qui évite de rejouer des inputs obsolètes ou en double.

## Vérifications

- Tests ciblés Wayland et transport : 14 tests réussis.
- npm test -- --runInBand --silent : 112 suites et 388 tests réussis.
- npm run check:style et git diff --check réussis.

## Suite

La reconnexion réseau et la restauration d'état côté client restent à traiter
dans une prochaine itération REL.
